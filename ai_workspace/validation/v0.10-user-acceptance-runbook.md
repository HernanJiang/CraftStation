## 前置条件（由你确认）

1. Codex 与 Grok Build 官方 runtime 均已登录、可计费，允许发起短 marker turn。

## Primary 路径：Codex source → Grok target

1. 创建/打开一个 Codex Thread（source），记录 Thread 标题、Model、Harness。
2. 创建/打开一个 Grok Build Thread（target，同项目）。
3. 在 source Thread 打开协作入口（Thread 头部协作按钮 → `ThreadCollaborationDialog`）。
4. 确认 target picker：显示对端 Model/Harness/status/worktree；**与本 Thread 完全相同 Model×Harness 的候选应被禁用并提示 Same Model and Harness**。
5. 默认 `after-current-turn` 模式发送一条带唯一 marker 的 request（不要勾选 context）。
6. 到 target timeline 确认 request 已到达；Grok 官方 Runtime 产生真实 assistant 回复。
7. 回到 source：exchange 卡片出现 reply 摘要（excerpt），确认 request item anchor / reply anchor 正确。
8. 在同一 ConversationLink 上继续发 follow-up，确认顺序与关联正确。

## 状态路径

- [ ] target 正在工作时发送请求 → 默认排队（durable queue），target 不被打断、不出现 steer。
- [ ] 切换 `interrupt-and-send` → 出现二次确认；取消则不发送。
- [ ] 制造一次 interrupt 确认失败（如 target 无法 settled）→ 请求不投递，错误码稳定可见。
- [ ] needs-attention（如 target 等待审批）→ exchange 进入 attention 状态；处理后继续投递。
- [ ] 取消：投递前取消（不发送）；投递后取消（只停止等待，不打断 target）。
- [ ] 跨 worktree target → 显示 cross-worktree warning，且不暗示文件/worktree 自动同步。
- [ ] 显式勾选 context → context summary 只包含所选内容；默认为空。

## Restart / 恢复

- [ ] 有 queued / in-flight / replied exchange 时关闭并重启应用 → exchange 状态正确恢复，无重复投递。
- [ ] 过期 claim（如模拟 worker 崩溃后重启）→ 不重复发送，状态 fail closed。

## 第二 Harness route

- [ ] 用 OpenCode + Kimi（或其他非 Codex/Grok 组合）重走一次 primary 路径（request → 真实回复 → follow-up）。

## Remote（可选但建议）

- [ ] Remote 端能看到 exchange 摘要（无 full request/context、无 idempotency/claim 内部值），read/wait/cancel 参与者策略正确。

## 记录要求

- 每项记录：通过 / 失败 / BLOCKED + 现象（截图或简述）。
- 不得保存：token、cookie、API key、完整敏感 context、hidden reasoning。
- 验收结果不改变自动化结论；PASS 与否最终由你确认，Debugger 独立 verdict 仍需在其路由恢复后另行完成。
